# Clay
Clay (short for C-Layout) is a UI layout library built in C. The design philosophy of Clay is to provide the tools for handling UI layout and events, and provide an API for a rendering backend to use to render a layout generated by Clay. 

## Workflow 
A typical workflow for a Clay application goes as such:
```c
int main(void) {
    Clay_App app;
    Clay_init(&app, ...);
    // Set the initial scene

    while (/* App is running */) {
        Clay_handleEvents(&app, ...);
        Clay_render(&app, ...);
    }
    return 0;
}
```
The following sections will explain what this code is doing and how it functions.

### App
All the data of the application is stored into the App struct:
```c
struct Clay_App {
    // All data needed for rendering the app
    Clay_Render render;
    // To avoid unnecessary renders
    atomic_int rerenderLayoutNextFrame;

    // Layout and event information for RenderBoxes
    Clay_Scene scene;

    // Global events and mouse state
    Clay_AppEvents events;
};

```
The App struct contains the data for rendering using Clay, setting the layout and events. 

### Layout
#### Scene
The main layout of the application is contained in the scene. A Scene has an ID, a function to compute its layout, rendering information, custom data and a function to free memory owned by the Scene.
```c
typedef struct Clay_Scene {
    Clay_SceneId sceneId;
    Clay_Layout sceneLayout;

    ComputeSceneLayout computeSceneLayout;
    TerminateScene terminateSceneFunction;
    void* data;
} Clay_Scene;
```
The Clay_Layout is a struct which contain an array of RenderBox.
```c
typedef struct Clay_Layout {
    Clay_Color bgColor;
    Clay_LayoutBox* layoutBoxes;
    size_t numLayoutBox;
} Clay_Layout;
```
Each Clay_LayoutBox contains all information about its position, rendering and event handling. There is also a isActive parameter. If set to true the Clay_LayoutBox is rendered and its events are handled. If set to false, the Clay_LayoutBox is not rendered and none of its events are handled.
```c
typedef struct Clay_LayoutBox {
    bool isActive;
    Clay_Rect renderRect;
    Clay_RenderFunction renderFunction;
    Clay_EventCallback onMouseButtonDown;
    Clay_EventCallback onMouseButtonUp;
    Clay_EventCallback onMouseEntered;
    Clay_EventCallback onMouseHovered;
    Clay_EventCallback onMouseExited;
    Clay_EventCallback onMouseWheelScrolled;
} Clay_LayoutBox;
```
The render function can use one of Clay primitives to draw things to the screen.
```c
typedef enum {
    CLAY_PRIMITIVE_BORDER_QUAD,
    CLAY_PRIMITIVE_FILLED_QUAD,
    CLAY_PRIMITIVE_TEXTURED_QUAD,
    CLAY_PRIMITIVE_TEXT
} ClayPrimitiveType;
```
To add a primitive to the layout, you can use the function `Clay_addPrimitive` with a parameter of a struct representing the primitive. Each primitive have different parameter which determine their position, size, type, color, texture or text if applicable, etc. 

Each primitive is added onto a render queue managed internally by Clay. Clay will then call specific functions which the rendering backend can implement. This is an important design decision of Clay:
- Clay defines *what* can be drawn
- The backend defines *how* it's drawn

### Events
Events are put in a queue and all events are handled when the function `Clay_handleEvents` is called. This function will dispatch events to all callbacks of the layout boxes and the global app events. This function will also update the mouse state. 

The global app events and mouse state are in the Clay_AppEvents struct.
```c
typedef Clay_AppResult(*Clay_EventCallback)(Clay_Event*, App*);

typedef struct Clay_MouseState {
    bool holdingLeftMouseButton;
    bool holdingRightMouseButton;
    Clay_Point mousePoint;
} Clay_MouseState;

typedef struct Clay_AppEvents {
    Clay_EventCallback onWindowResize;
    Clay_EventCallback onKeyDown;
    Clay_EventCallback onTextInput;

    Clay_MouseState mouseState;
    atomic_int shouldHandleEvents;
} Clay_AppEvents;
```
The callbacks of events specific to a Clay_LayoutBox will only get called if the mouse clicked in the render rectangle of the layout box or if it is hovering the rectangle. This is the same of the mouse wheel, the mouse needs to be hovering the layout box 

### Rendering
The function `Clay_render` will handle the dispatching of Clay primitives to the rendering backend. This function will also run if the `rerenderLayoutNextFrame` field in the Clay_App struct is set to `MAIN_THREAD_RERENDER` or `OTHER_THREAD_RERENDER`. Before this function returns, this parameter will be set to `NO_RERENDER`, which will disable the dispatching of the layout to avoid unnecessary rerenders of the UI. This is the logic of the `Clay_render` involving the `rerenderLayoutNextFrame` field.
```c
SDL_AppResult render(App* app) {
    // We only rerender if we are told so
    if (atomic_load(&app->shouldRenderApp) == NO_RERENDER) {
        return SDL_APP_CONTINUE;
    }
    else if (atomic_load(&app->shouldRenderApp) == OTHER_THREAD_RERENDER) {
        // If we already have a OTHER_THREAD_RERENDER value then we don't want to rerender twice
        // so we set the value to MAIN_THREAD_RERENDER
        atomic_store(&app->shouldRenderApp, MAIN_THREAD_RERENDER);
    }
    /*
        ...
        Logic for dispatching the layout to the rendering backend
        ...
    */

    // After we rerender, we assume that shouldRender is either OTHER_THREAD or MAIN_THREAD
    // This means that if shouldRender is NO_RERENDER then it will stay that way
    // else we go to a main thread rerender so that we rerender once more before stopping
    if (atomic_load(&app->shouldRenderApp) == OTHER_THREAD_RERENDER) {
        atomic_store(&app->shouldRenderApp, MAIN_THREAD_RERENDER);
    }
    else {
        atomic_store(&app->shouldRenderApp, NO_RERENDER);
    }

    return returnValue;
}

```
